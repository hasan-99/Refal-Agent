## Existing interfaces and boundaries to reuse

- `src/supabaseStore.js` is `EdgeApiStore`: request uses the anon/publishable bearer plus `x-rafa-api-secret`; no local service-role database client exists here. Add read/write methods over authenticated Edge routes. The Edge function already has its server-side Supabase service client. A service-only table cannot be made readable by the dashboard's existing anon REST helper without a new trusted transport.
- `supabase/functions/rafa-agent-api/index.ts` checks `rafa_validate_api_secret` before routing. `workflowContact` resolves actual contact and validates source-turn ownership. Existing workflow methods return selected persisted rows. Role authorization for operator CRUD must additionally originate from validated dashboard sessions, never a body role flag or editable user metadata.
- Dashboard `/api` routes pass `requireAuth`; mutations normally use `requireAdmin`. Reuse `req.dashboardUser` as actor source. `supabaseRest` uses a dashboard shared secret with historical RLS denial concerns (CF-06); an empty HTTP 200 result is not proof of an empty table or successful mutation.
- `src/agentRuntime.js:buildToolContext` currently binds store, user/userId, intents/language, inboundMessageId and booking policy. Pass current customer message/source turn and trusted capabilities/role here, not in model-controlled args. The default loop budget is four steps; a combined inclusions/live-value request must fit or have an explicit bounded budget policy.
- Both `src/agentDecision.js:formatApprovedKnowledgeEvidence` and `src/groundingPolicy.js:collectApprovedKnowledgeEvidence` only understand `modelObservation.type === approved_knowledge`. Dynamic observations need an explicitly bounded safe channel in both formatter and grounding. Raw tool data must not be exposed accidentally. Source metadata must reach the reservation guard as trusted provenance rather than a model assertion.
- `src/messageRouter.js:recordHistory` already persists handover/compliance records after storing the conversation turn and sends internal handover notifications. A second action path must reconcile that state to avoid duplicate writes and notifications. `createHandover` utility builds a summary; `store.createHandover` actually persists it. `proposeHandover` is authorization only.
- Reuse `src/agentBookingTools.js`: it requires inboundMessageId, stable idempotency, policy-valid slot, persisted appointment id and real calendar confirmation. `pending_review` is a successful request, not a confirmed booking. Existing slot lock is process-local; durable appointment key is the cross-process guarantee.
- Reuse `store.saveFollowUpState`, but integrate scheduling with `src/followUp.js`: current timing ignores `followUpState.next_due_at` and uses last-message time plus global delay. Saving a due date alone does not schedule that requested time. Consent must be rechecked at dispatch, and scheduling must never claim a message was sent.
- Reuse `store.logAuditEvent` and `store.createPriorityAlert` for compliance records/alerts. Preserve redaction: existing compliance payload stores trigger labels, language and timestamps, not sensitive customer prose. An optional logger resolving undefined is not proof of durable audit persistence.

## Ambiguities resolved conservatively

1. “Six commercial tables” includes the lead table; calendar slots use existing appointments. Do not create a seventh slot table.
2. P4.1 owns CF-05 despite tools being P4.2. Build the minimal offer-read/composition dependency before closing P4.1, then reuse it during registry integration. Keep the checkbox open if live deployment remains pending.
3. The strict live-data exit and P4.3's explicit formation-chunk exception coexist: retain the documented 30-day legacy health allowance, but current prices still require a live offer read and live data wins conflicts. Do not silently revise the source plan or widen other numeric exceptions.
4. Section 20 labels lead-profile MIG-07 under P8.1 while P4.1 explicitly creates the base table. Create the M4 base now; M8 extends it. Record the mapping in phase evidence.
5. P4.5's “hands off to M12” means typed forms are M4 acceptance, with later admin expansion in M12.
6. Static programme thresholds/tax rates are approved knowledge, not unit prices or active promotions. Currency warning and dynamic health classification must not ban every approved programme amount indiscriminately.

## Local verification availability

Initial read-only command discovery found no `docker`, `psql`, `pg_ctl`, `initdb` or `supabase` on PATH; no installed PostgreSQL/Docker directories or PGlite/pg-mem dependency were found in the checked standard locations. This does not establish that installation is impossible. A disposable local PostgreSQL/PGlite installation can execute SQL without touching production; create Supabase role/contact/trigger prerequisites in the fixture and label evidence as local. Use actual PostgreSQL role checks and constraint probes; a text matcher is not a migration run. Existing `scripts/querySupabaseReadOnly.ps1` can inspect remote schema/history safely through the Management API if separately used. No remote reads or writes were performed for this analysis.
