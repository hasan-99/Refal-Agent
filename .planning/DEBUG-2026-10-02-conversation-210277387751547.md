# Conversation Diagnostic — 2026-10-02

**Scope:** Read-only inspection of the supplied WhatsApp conversation and its stored workflow records. Personal identifiers and customer-provided contact text are intentionally omitted.

## Findings

1. **Bad customer name in specialist handover.** The Arabic conversation begins with a greeting and small talk, then turns into a company/investment enquiry. The resulting investment handover stored an earlier greeting/service question as the customer's name. That bad value passed through `buildRefalLeadSummary()` because it used `safeValue()` (PII/control-character cleanup only), not name validation. The current inbound router has a name plausibility check, but the summary builder was not a final validation boundary.

2. **Malformed internal requirements.** The same handover stored the literal `[object Object]` in its free-text `requirements` field. `conversation.requirements` can be a structured object; coercing it through `String()` loses all useful detail.

3. **Conversation progress was mostly relevant after the project was understood.** A short acknowledgement was classified `unknown`; later company setup and cost turns retrieved approved LAMAR company-formation evidence, and the displayed price answer cited the published package while asking to confirm current terms. The unclear investment request was routed high-priority to an open specialist handover. Ten of the fifteen turns had retrieval evidence; greetings/small talk did not retrieve knowledge. Exact provider/stage latency is not present in the stored turn metadata, so no per-stage timing claim is possible.

4. **Specialist follow-up outcome needs clear admin visibility.** A consented email follow-up is recorded in turn metadata, and the contact has an open investment handover. No notification-delivery job is linked to that handover. The dashboard handover row is the durable review item; an email/WhatsApp notification is not the same thing and must not be implied as sent. This diagnostic did not send anything or mutate follow-up state.

5. **Older booking records remain for admin review.** Two records from the previous day remain `pending_calendar`, including one whose purpose describes a visa request. They are not created by the inspected day's turns and are not confirmed appointments. They were left untouched because changing or cancelling live customer booking records requires an explicit operator decision.

6. **Language signal worth addressing separately.** A turn containing only an email address was classified as English, and the reply switched to English before subsequent Arabic turns returned to Arabic. The current script-count detector treats Latin characters in contact data as conversational English. This is a reproducible general language-detection gap, but was not changed in this minimal pass because the language fallback must be made consistent across the WhatsApp worker and Edge Function and tested through that live path.

## Fix Applied

- `src/handover.js`: validate the customer name at the summary boundary and reject non-name text; render structured requirement objects as bounded key/value text rather than JavaScript's `[object Object]` coercion.
- `supabase/functions/rafa-agent-api/handoverPersistence.mjs` and `index.ts`: repeat both safeguards at the server persistence boundary, including when merging into an existing active handover.
- `src/handover.test.js` and `dashboard/handoverPersistence.test.js`: regression tests for both boundaries and legacy bad summaries.
